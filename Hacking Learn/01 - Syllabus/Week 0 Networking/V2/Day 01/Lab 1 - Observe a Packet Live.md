## 1. Lab overview — seeing the internet for the first time 👁️

This lab is the first time you stop trusting diagrams and start trusting your own eyes. Up to now, “packets” have been something you read about: little boxes on slides, arrows on network diagrams, abstractions in textbooks. In this lab, you will capture a real packet as it moves between two machines, freeze it in a pcap, and then peel it apart layer by layer until there is nothing left unexplained. You will see the Ethernet header that lets it survive on the local wire, the IP header that lets it traverse networks, the ICMP header that defines its purpose, and the payload that carries its content.

The goal is not to prove that packets exist. The goal is to make them feel real. When you are done, you should be able to look at any future pcap and feel a kind of déjà vu: “I know what this is. I’ve seen this creature before. I know how it’s built and why it looks this way.”

This lab is deliberately small. One packet. One ping. One capture. But inside that single packet is the entire philosophy of networking: addressing, encapsulation, layering, and the idea that communication is just structured movement.

## 2. Learning goals — what this lab teaches you 🎯

By the end of this lab, you should be able to describe a packet in concrete, physical terms. You should be able to say, without hand‑waving, what fields exist in the Ethernet header, what fields exist in the IP header, what fields exist in the ICMP header, and what the payload is doing. You should be able to explain why a packet has both MAC addresses and IP addresses, why those addresses are different, and how they work together to get the packet from one host to another.

You should also be able to connect the commands you run to the packets you see. When you type `ping -c 1 192.168.20.20` on Kali, you should be able to point to a specific packet in Wireshark and say: “That is the Echo Request generated by that command. That is the Echo Reply generated by Ubuntu. This is the exact moment my terminal printed ‘64 bytes from…’.”

Finally, you should come away with a sense that tcpdump and Wireshark are not magic tools but microscopes. They do not create packets. They do not alter packets. They simply let you see what is already happening.

## 4. Deep theory — what a packet actually is 🔬

A packet is not a file. It is not a document. It is not a static object that sits somewhere waiting to be opened. A packet is a transient event. It exists only while it is moving. Once it reaches its destination and is processed by the receiving host, it ceases to exist as a packet. The only reason you can capture a packet is because you intercept it mid‑flight and freeze it in a pcap file.

At a structural level, a packet is a series of nested headers wrapped around a payload. The outermost header, in this lab, is the Ethernet header. It contains the source MAC address and destination MAC address, which identify the sender and receiver on the local network segment. It also contains an EtherType field that tells the receiving host what kind of payload is inside — in this case, an IPv4 packet.

Inside the Ethernet frame is the IP header. This header contains the source IP address and destination IP address, which identify the logical endpoints of the communication. It also contains fields like the Time To Live (TTL), which prevents packets from looping forever, and the Protocol field, which tells the receiving host what kind of transport or control protocol is inside — in this lab, ICMP.

Inside the IP packet is the ICMP header. ICMP is the Internet Control Message Protocol, used for diagnostic and control messages. The Echo Request and Echo Reply used by `ping` are just two of many ICMP message types. The ICMP header contains a Type field (8 for Echo Request, 0 for Echo Reply), a Code field (usually 0 for these messages), a checksum, and additional fields like an identifier and sequence number that allow the sender to match replies to requests.

Finally, inside the ICMP message is the payload. For `ping`, this often includes a timestamp and some arbitrary bytes. The payload is not important to the network itself; it is important to the application or tool using ICMP.

When you look at a packet in Wireshark, you are seeing these layers presented as a tree. But on the wire, they are just bytes in a specific order. The network does not see “Ethernet, then IP, then ICMP.” It sees a stream of bits and interprets them according to the rules of each layer.

This lab is about making that interpretation explicit. You will not just see that a packet exists. You will see how it is built and why it is built that way.

## 5. Experiment design — how to force the network to reveal itself 🧪

To observe a packet, you need three things: a vantage point where packets pass by, a predictable packet to capture, and a tool to freeze the packet in time.

pfSense’s LAN interface is your vantage point. Every packet that moves between Kali and Ubuntu must cross that interface. If you run tcpdump there, you will see those packets.

The predictable packet will be an ICMP Echo Request generated by `ping` on Kali and sent to Ubuntu. This choice is deliberate. ICMP Echo Requests and Echo Replies are small, simple, and easy to recognize. They are also ubiquitous in network troubleshooting, so understanding them deeply will pay off in every future lab.

The tool to freeze the packet is tcpdump. It will listen on pfSense’s LAN interface, filter for ICMP traffic, and write any matching packets to a pcap file. Later, you will open that pcap in Wireshark and dissect the packet.

The experiment is intentionally minimal. You are not scanning a network. You are not generating thousands of packets. You are creating one packet on purpose, capturing it, and studying it. The simplicity is what makes the learning sharp.

## 6. Walkthrough part 1 — preparing the capture vantage point on pfSense 🛠️

The first step is to position your “microscope” at the right place in the network. That microscope is tcpdump, and the right place is pfSense’s LAN interface.

On pfSense, you start tcpdump with a command that both captures the right traffic and preserves it for later analysis:

```bash
sudo tcpdump -i eth0 -w ~/day1_lab1/pcaps/packet_observation_$(date -u +"%Y%m%dT%H%M%SZ").pcap icmp &
echo $! > ~/day1_lab1/artifacts/tcpdump_packet_observation_pid_$(date -u +"%Y%m%dT%H%M%SZ").txt
```

The `-i eth0` argument tells tcpdump which interface to listen on. In your lab, `eth0` is the LAN interface where traffic between Kali and Ubuntu flows. If your interface name is different, you would adjust this, but the concept is the same: you are choosing the artery you want to listen to.

The `-w` argument tells tcpdump to write the captured packets to a file instead of printing them to the screen. The filename includes `packet_observation_` and an ISO‑style UTC timestamp, which makes it easy to correlate this capture with other artifacts later.

The final `icmp` argument is a capture filter. It tells tcpdump to only capture ICMP packets. This keeps the pcap small and focused. You are not interested in every packet on the network right now. You are interested in the specific ICMP Echo Request and Echo Reply that `ping` will generate.

The `&` at the end runs tcpdump in the background, allowing you to continue using the shell. The `echo $!` command writes the process ID of tcpdump into a file in the `artifacts` directory. This gives you a reliable way to stop the capture later without guessing or manually hunting for the process.

Conceptually, what you have done is set up a camera at the intersection. Nothing has happened yet. No packets have passed. But the camera is rolling, and when something does happen, it will be recorded.

## 7. Walkthrough part 2 — generating a single, intentional packet from Kali 📡

With tcpdump listening on pfSense, you now need to generate the packet you want to observe. That packet will be an ICMP Echo Request sent from Kali to Ubuntu.

On Kali, you run:

```bash
ping -c 1 192.168.20.20 | tee ~/day1_lab1/scans/kali_ping_output_$(date -u +"%Y%m%dT%H%M%SZ").txt
```

The `ping` command sends ICMP Echo Requests to the specified IP address. The `-c 1` option tells it to send exactly one request and then stop. This is important. You want a clean, simple capture with a single request and a single reply, not a flood of packets.

The destination IP `192.168.20.20` is Ubuntu’s address on the local network. When you press Enter, Kali begins the process of constructing and sending the packet.

First, Kali checks its ARP cache to see if it already knows the MAC address associated with `192.168.20.20`. If it does not, it broadcasts an ARP request on the local network, asking “Who has 192.168.20.20? Tell 192.168.20.10.” Ubuntu responds with its MAC address. Kali stores this in its ARP cache.

Once Kali knows Ubuntu’s MAC address, it constructs an Ethernet frame. It sets the destination MAC to Ubuntu’s MAC, the source MAC to its own, and the EtherType to indicate that the payload is an IPv4 packet.

Inside that Ethernet frame, Kali constructs an IP packet. It sets the source IP to `192.168.20.10`, the destination IP to `192.168.20.20`, the TTL to a default value (often 64), and the Protocol field to indicate ICMP.

Inside that IP packet, Kali constructs an ICMP Echo Request. It sets the Type field to 8 (Echo Request), the Code field to 0, and fills in an identifier and sequence number. It then adds a payload, which often includes a timestamp and some arbitrary bytes.

Finally, Kali sends the frame onto the wire. The packet begins its journey from Kali to Ubuntu, passing through pfSense’s LAN interface along the way.

The `tee` command in your `ping` line writes the output of `ping` to a file in the `scans` directory while also displaying it on the screen. This gives you a record of what Kali saw: the fact that it sent one packet, received one reply, and measured the round‑trip time.

From your perspective, you typed a command and saw a line of text. From the network’s perspective, a carefully structured packet was created, addressed, and launched.

## 8. Walkthrough part 3 — freezing the packet in time and verifying the capture 👀

While Kali was constructing and sending the ICMP Echo Request, tcpdump on pfSense was quietly listening. When the packet crossed pfSense’s LAN interface, tcpdump captured it and wrote it to the pcap file. When Ubuntu replied with an ICMP Echo Reply, that packet also crossed pfSense and was captured.

Now that the ping has completed, you stop the capture on pfSense:

```bash
kill $(cat ~/day1_lab1/artifacts/tcpdump_packet_observation_pid_*.txt) || true
```

This command reads the process ID of tcpdump from the file you created earlier and sends it a termination signal. The `|| true` at the end ensures that even if the `kill` command complains (for example, if the process has already exited), your script or shell session does not break.

At this moment, the pcap file is complete. It contains a record of the ICMP packets that crossed pfSense’s LAN interface during the capture window. The packets themselves no longer exist on the wire. They have already been processed by Ubuntu and Kali. But their structure and contents have been preserved in the pcap.

To verify that the capture worked, you can run:

```bash
tcpdump -r ~/day1_lab1/pcaps/packet_observation_*.pcap
```

This reads the pcap file and prints a summary of each packet. You should see at least two lines: one for the ICMP Echo Request from Kali to Ubuntu, and one for the ICMP Echo Reply from Ubuntu to Kali. The timestamps on these lines will be very close together, reflecting the short round‑trip time on a local network.

This is your first confirmation that the experiment succeeded. You generated a packet, captured it, and can now see evidence of its existence.

## 9. Walkthrough part 4 — dissecting the packet in Wireshark, layer by layer 🔍

Now comes the part where the packet stops being a line of text and becomes a structured object you can explore. You open the pcap in Wireshark:

```bash
wireshark ~/day1_lab1/pcaps/packet_observation_*.pcap
```

When Wireshark opens, you see a list of packets. You apply a display filter to focus on ICMP:

```text
icmp
```

You click on the ICMP Echo Request. Wireshark shows you three main panes: a summary list of packets at the top, a tree view of the selected packet’s protocol layers in the middle, and a raw hex/ASCII view at the bottom.

In the middle pane, you see an “Ethernet II” section. You expand it. You see the destination MAC address, which belongs to Ubuntu, and the source MAC address, which belongs to Kali. You see the EtherType field indicating that the payload is an IPv4 packet. This is the Layer 2 view of the packet: how it is delivered on the local network.

You expand the “Internet Protocol Version 4” section. You see the source IP address `192.168.20.10` and the destination IP address `192.168.20.20`. You see the version, header length, total length, identification, flags, fragment offset, TTL, protocol, header checksum, and possibly some options. The Protocol field is set to 1, which corresponds to ICMP. This is the Layer 3 view of the packet: how it is delivered across networks.

You expand the “Internet Control Message Protocol” section. You see that the Type is 8 (Echo Request) and the Code is 0. You see the checksum, the identifier, and the sequence number. You may see a timestamp or other data in the payload. This is the Layer 4+ view of the packet: what kind of control message it is and how it can be matched to a reply.

You scroll down to the raw hex/ASCII view. You can see the bytes that make up the packet. If you look closely, you can see the ASCII representation of the payload, often including a timestamp or the string that `ping` uses.

You then click on the ICMP Echo Reply. You repeat the process. You see that the source and destination MAC addresses are reversed. The source IP is now `192.168.20.20` and the destination IP is `192.168.20.10`. The ICMP Type is now 0 (Echo Reply). The identifier and sequence number match the request. The payload is the same size.

By doing this, you are not just looking at packets. You are reading them. You are seeing how the network encodes meaning into structure.

## 10. Walkthrough part 5 — tying the packet back to commands, hosts, and intent 🧠

It is easy to treat Wireshark as a separate universe, a place where packets live in isolation. But the real power comes from tying what you see in Wireshark back to the commands you ran and the hosts that ran them.

You look at the timestamp of the ICMP Echo Request in Wireshark. You compare it to the timestamp in the filename of your `kali_ping_output_*.txt` file. They line up. You open the ping output file:

```bash
cat ~/day1_lab1/scans/kali_ping_output_*.txt
```

You see something like:

```text
PING 192.168.20.20 (192.168.20.20) 56(84) bytes of data.
64 bytes from 192.168.20.20: icmp_seq=1 ttl=64 time=0.XXX ms

--- 192.168.20.20 ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.XXX/0.XXX/0.XXX/0.000 ms
```

You realize that the “1 packets transmitted” line corresponds to the ICMP Echo Request you saw in Wireshark. The “1 received” line corresponds to the Echo Reply. The `ttl=64` value in the ping output corresponds to the TTL field in the IP header of the Echo Reply. The `time=0.XXX ms` value corresponds to the difference between the timestamps of the request and reply in the pcap.

You now have a closed loop. A command you ran on Kali produced a packet. That packet crossed pfSense and was captured. That packet was processed by Ubuntu, which produced a reply. That reply crossed pfSense and was captured. The reply was processed by Kali, which printed a line of text. Every step of that loop is visible in your artifacts.

This is the essence of packet‑level understanding: being able to connect human‑level actions to network‑level events.

## 12. Failure modes, debugging, and deeper reasoning 🧰

Things will not always work as cleanly as they did in the ideal path above. Those failures are not annoyances; they are opportunities to deepen your understanding.

If you open the pcap and see no packets, you might have captured on the wrong interface. Maybe `eth0` is not the LAN interface. You can run `ip addr` or `ifconfig` on pfSense to confirm which interface has the `192.168.20.1` address. You can adjust your tcpdump command accordingly.

If the ping fails with “Destination Host Unreachable” or “Request timed out,” you might have a routing or firewall issue. Maybe Ubuntu is not up. Maybe pfSense is blocking ICMP. Maybe Kali has the wrong default gateway. Each of these possibilities forces you to think about how packets move and what assumptions you are making.

If you see ARP requests in the pcap but no ICMP packets, it might mean that Kali is trying to discover Ubuntu’s MAC address but never gets a reply. That suggests a link‑layer problem: maybe Ubuntu is down, or maybe it is on a different VLAN.

If you see the Echo Request in the pcap but no Echo Reply, it might mean that the packet reached Ubuntu but was not processed, or that the reply was blocked on the way back. That suggests a host‑level or firewall issue.

In each case, the failure is not just “it didn’t work.” It is a specific pattern of packets — or lack of packets — that tells you where in the path things broke.
